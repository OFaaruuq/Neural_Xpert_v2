Integration · Enterprise Applications · Intelligent Automation

A model that cannot see the live record, and cannot hand its result back to the system where work happens, stays a side project. Integration is how AI becomes part of the business: it reads the applications and data people already trust, and it returns an outcome those applications can store, route, or measure.

Name the outcome in the system of record

Start from the transaction, not the model. What should be different in the CRM, the case tool, the ERP, or the data warehouse when the AI step works? Examples:

  • A case is classified and routed with the fields filled from the source document.
  • A forecast is written to the planning system on a schedule.
  • A draft reply is attached to the customer record for an agent to send.
  • An exception is opened for a person because confidence was too low.

If the result only appears in a chat log, the business cannot manage it. Put the result where the existing process already looks.

Integrate through contracts, not screen scraping

Prefer the API, event, or data product the application owner already supports. A stable contract says which fields exist, what they mean, who may call them, and what happens when a call is repeated. Screen scraping and shared database passwords break on the next release and hide the dependency from the team that owns the system.

When an API does not exist, the integration work includes getting one. That is slower than a shortcut and much cheaper than an automation that fails silently after an interface change.

Use the caller’s identity

The AI step should act as the user it assists or as a service account with a narrow role. It should not reuse an integration account that can see every customer. Map the company identity provider through to the target application so a permission change for the person also limits the automation.

Secrets belong in a vault, rotated, and absent from notebooks and prompt logs. An API key pasted into a prompt will leave in the log.

Make every write safe to repeat

Networks fail and jobs retry. A write that creates a second order, a second email, or a second case on retry is a defect. Design updates to be idempotent: the same request, sent twice, leaves the system of record in the same state. Store an identifier for the AI run on the record so operators can see which automation touched it.

Separate suggest from commit

Reading data to prepare a recommendation is a different integration from posting a change. Ship the read path and the draft first. Add the write when the error rate is known and the write can be reversed or reviewed. For high-impact fields, the integration should open a task for a person rather than update the field directly.

Agree the data, then the model

AI quality follows data quality. Before tuning a model, confirm that the fields it needs are present, current, and mean the same thing in each source. Document the grain: one row per customer, per order, or per day. A model trained on a joined extract that production cannot reproduce will look accurate in a notebook and useless in the application.

Lineage matters when someone asks why a record was classified a certain way. Keep the source identifiers with the prediction.

Measure the workflow after the handoff

Count the business result, not the number of API calls. Useful measures are cycle time, the share of cases completed without rework, the rate of human override, and the cost of a wrong commit. If those numbers do not move, the integration may be technically healthy and still the wrong place to apply AI.

Give application owners a dashboard they recognize: failures, latency, and the records the automation changed. An AI platform that only the data science team can see will not survive the first incident.

A sequence that respects the systems already running

1. Write the outcome as a change in the system of record.

2. Use a supported API and the caller’s identity.

3. Read and draft before anything is committed.

4. Make writes idempotent and traceable.

5. Report override rate and cycle time to the team that owns the process.
